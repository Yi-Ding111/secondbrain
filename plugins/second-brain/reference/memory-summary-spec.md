# 记忆总结规范 — Memory Summary Spec

这份文件是**任务收尾总结**的权威成文规范。凡是产出"一次任务做了什么"的总结——`/wrap-work`（个人机）、`work-capture`（工作机）、以及 `meta/templates/task.md` 模板——都必须遵守本规范。

核心立场一句话：**总结是为了"日后快速回忆 + 沉淀经验"，不是为了记录代码变更。** 代码变更 git 已经存了；总结要留下的是 git 存不下的东西——当时的逻辑、踩的坑、怎么解的、为什么这么选。

---

## 1. 必含项（缺一不合规）

一份合规的任务总结**必须**包含以下五块。若某块确实不适用，写一句"本次无"而不是省略。

### ① 流程图（mermaid）

用一张 `mermaid` 图表达这次任务的**实现逻辑或数据/控制流**，并在图里体现**关键问题分支与解决路径**（哪条路走通了、哪条是死胡同）。图是"一眼回忆"的最强抓手，优先于文字。

### ② 实现逻辑叙述

用 prose 讲清楚**做了什么、怎么做的、为什么这样做**——是思路和方法，不是文件清单。读者读完应能复述这次实现的骨架，而不需要打开代码。

### ③ 实质问题 → 解决路径 → 方案

这是总结里**最值钱**的部分。逐个列出过程中遇到的**实质性问题**（不是打字错、不是琐碎编译错），每个写清：

- **现象 / 卡在哪**：问题长什么样。
- **根因**：真正的原因（往往和第一直觉不同）。
- **尝试过的路径**：走过哪些弯路、为什么不行——弯路本身就是经验。
- **最终方案**：怎么解决的。

### ④ 关键决策

这次做的**取舍**：选了什么、放弃了什么、**为什么**、trade-off 是什么。日后"当初为什么这么设计"的答案就靠这块。

### ⑤ 回忆钩子（Recall Hooks）

3–6 条极短 bullet，是给未来的自己的"记忆索引"——扫一眼就能瞬间想起这次任务的抓手。例如"就是那次为了绕开 X 限制、改用 Y 的任务"。这是 Yi 特别看重的"快速回忆"入口，**必写**。

## 2. 禁止项（出现即不合规）

以下内容**不要**写进总结——它们是噪音，git/diff 工具已经能提供，塞进记忆只会稀释信号：

- ❌ **文件 / 行号级 diff**：如 `M path/to/foo.ts (+12 -3)`、"第 42 行改成……"。
- ❌ **机械改动文件清单**：逐个列"改了哪些文件"。
- ❌ **逐 commit 流水账**：按 commit 罗列 hash / author / subject。
- ❌ **Before / After 代码块堆砌**：大段贴改动前后的代码。
- ❌ 任何"把 git log / git diff 抄一遍"性质的内容。

> 例外：如果某一小段代码**本身就是关键决策的核心**（如一个精妙的算法、一处反直觉的 fix），可以贴**几行**并解释它为什么重要。区别在于——是为了"讲清一个决策/方案"，而不是为了"记录改动"。

## 3. 正反例对照

同一个任务，两种写法。旧模板 `meta/templates/task.md` 里的 `Commit Timeline` / `Files Changed` / `Before / After` 三节就是**反例样板**。

### ❌ 反例（旧风格，禁止）

```
## Commit Timeline
### 1. a1b2c3d — 2026-07-10 14:22 — fix retry
Files touched:
- M src/worker/retry.ts (+18 -4)
- M src/worker/config.ts (+2 -0)
做了什么: 改了 retry 逻辑

## Files Changed
- src/worker/retry.ts — modified (+18 -4)
- src/worker/config.ts — modified (+2 -0)

## Before / After
### src/worker/retry.ts — retry()
Before: ```for (i=0;i<3;i++)...```
After:  ```while (attempt < maxAttempts)...```
```

读完这些，半年后的你**依然不知道**：为什么要改 retry？原来的 retry 出了什么事？为什么是 while 不是 for？

### ✅ 正例（记忆风格）

> **概述**：worker 在下游 503 时会把任务永久丢弃，本次改成有上限的指数退避重试，止住了偶发的任务丢失。
>
> **流程图**：
> ```mermaid
> flowchart TD
>   A[收到任务] --> B[调用下游]
>   B -->|200| C[完成]
>   B -->|503| D{尝试次数 < 上限?}
>   D -->|是| E[指数退避后重试] --> B
>   D -->|否| F[进死信队列, 告警]
> ```
>
> **问题 → 方案**：现象是每天零星几个任务无声消失。根因是旧代码把下游 503 当成永久失败直接 drop。**弯路**：先怀疑是消息队列 ack 丢了，查了半天 broker 日志无果；后来加了下游状态码埋点才定位到 503 分支。最终方案：对 503/超时做**有上限的指数退避**，超限进死信队列并告警，而不是静默丢弃。
>
> **关键决策**：选"指数退避 + 死信队列"而非"无限重试"——避免下游长时间挂掉时把自己拖垮；上限设 5 次是因为下游 SLA 恢复通常在 30s 内。
>
> **回忆钩子**：就是那次"任务零星消失"的排查；503 被当永久失败 drop 是根因；埋点才是破案关键。

同样一次改动，正例让未来的你**秒懂来龙去脉**，且沉淀了"下次遇到静默丢任务，先加状态码埋点"的经验。

## 4. 适用范围

- **`/wrap-work`（个人机）**：产出的 Tier-1 task 文件按本规范组织。
- **`work-capture`（工作机）**：把 AI thread 整理成可携带文案时按本规范组织。
- **`meta/templates/task.md`**：模板结构即本规范的落地形态。
- **mermaid 绘图约定**的进一步细化见 §6；本规范只要求"必有一张能表达问题分支的流程图"。

## 5. 一句话验收标准

> 把一份总结遮住代码，只留文字与图——半年后的你能不能凭它**复述这次做了什么、为什么、踩了什么坑**？能，则合规；只剩"改了哪些文件"，则不合规。

## 6. mermaid 流程图约定

约束三处一致：task 模板、`wrap-work` 产出、`work-capture` 生成。

- **何时画**：每份 task 记忆**必画**一张主流程图（必含项 ①）。"改动前/改动后架构"两张**仅当结构性变化时**各画一张，否则省。
- **图类型**：统一 `flowchart TD`（或 `graph TD`）的**通用语法**，不用专有扩展——Obsidian 与 Plane 都能渲染。
- **必须表达"踩坑 → 解决"分支**（Yi 最看重，别只画理想路径）：主流程走 happy path，问题点用带标签的分支引出根因与解决路径：
  ```mermaid
  flowchart TD
    A[起点] --> B{关键步骤}
    B -->|成功| C[完成]
    B -->|失败/超时| F[根因: …]
    F --> G[解决路径] --> B
  ```
- **粒度**：节点是**逻辑步骤 / 决策 / 组件**，不是代码行或文件。5–12 个节点为宜——太细则合并，太粗则拆分。
- **命名**：节点用简短名词短语；边标签写"事件 / 条件 / 失败原因"（如 `-->|503| …`）。判断节点用 `{…}`，普通步骤用 `[…]`。
