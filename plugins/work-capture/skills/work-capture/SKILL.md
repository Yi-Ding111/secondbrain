# Work Capture

把**当前 AI thread 对话**整理成一份**可直接复制、自包含**的结构化记忆文案。

这是一个**独立工具**:它只做"对话 → 好文案"这一件事,**不知道、也不关心这份文案最后会被怎么用**——你可以粘进笔记库、贴进文档、发给别人、或什么都不做。任何"这文案该往哪放、怎么归档"的判断都不属于本工具。

只依赖 thread 文本,不读代码库、不写任何文件、不假设任何环境。

## When to use
- 一段 AI 对话(调试 / 设计 / 实现 / 思考)结束,想把"做了什么、怎么解决、关键决策"整理成一份能带走的记忆。
- 用户说 "work-capture" / "整理这次对话" / "生成记忆"。

## 记忆格式(自包含，规则内嵌于此)

产出是**记忆**,不是代码变更记录。git/diff 能存的不写;写 git 存不下的:逻辑、踩的坑、怎么解、为什么这么选。

**必含 6 段**(缺项写"本次无"):
1. **概述** — 目标 / 为什么 / 解决了什么(1-3 句)
2. **流程图(mermaid)** — 主流程 + **问题分支/解决路径**(**必产**,见下约定)
3. **实现逻辑** — 做了什么、怎么做、为什么(prose,非文件清单)
4. **问题与方案** — 每个实质问题:现象 / 根因 / 走过的弯路 / 最终方案
5. **关键决策** — 取舍 + trade-off + 为什么
6. **回忆钩子** — 3-6 条"日后一眼想起"的抓手

**禁止**:文件/行号 diff、机械改动文件清单、逐 commit 流水账、Before-After 代码堆砌。若某几行代码是决策核心,可贴几行并解释**为什么重要**。

**mermaid 约定**:统一 `flowchart TD` 通用语法(任意 markdown 渲染器都能显示);节点是逻辑步骤/决策/组件(5–12 个),不是代码行;**必须**用带标签分支表达"踩坑→解决",如 `B -->|失败/超时| F[根因] --> G[解决路径]`;判断用 `{}`,步骤用 `[]`。

## Workflow

### Step 1 — 从 thread 抽取(不罗列改动)
通读当前对话,抽出:
- **解决了什么问题 / 目标**(→ 概述)
- **实现逻辑**:整体思路与方法
- **实质问题 → 根因 → 走过的弯路 → 最终方案**:对话里"卡住—尝试—失败—换法—通了"的地方就是金矿
- **关键决策 + trade-off**
- **流程图素材**:主流程 + 问题分支
琐碎报错、纯代码行不抽。代码改动 → 翻译成"做了什么/为什么"。

### Step 2 — 生成 mermaid 流程图
按上面约定画一张 `flowchart TD`,体现关键问题分支与解决路径。

### Step 3 — 组装自包含 markdown
按 [[OUTPUT-FORMAT]](同 plugin 内 `../../OUTPUT-FORMAT.md`):frontmatter(`source: work-capture` + `title` / `date` / `topic` / `tags`,可选 `project` / `ticket`)+ 6 段正文。

- **project / ticket** 只是**可选的通用元数据**——填了帮日后检索,不填也行。ticket 只写编号,**不复制**其正文。
- 全部内容在**一个文件**里:无外部依赖、无 `[[link]]`——纯文本 + 一个 mermaid block。

### Step 4 — 交付
把整份 markdown 作为**代码块**呈现给用户,方便一键复制。到此为止——文案交出去,怎么用是用户的事。

## 验收
拿一个真实 thread 跑 → 得到一份**可粘贴、图文完整、无行号 diff、单独打开即完整可读**的记忆文案。

## Anti-patterns
- ❌ 罗列"改了哪些文件/哪几行"
- ❌ 用 `[[wiki-link]]` 或假设某个知识库结构 —— 本文案要自包含、与下游无关
- ❌ 试图读代码库 / 写文件 —— 本 skill 只读 thread、只输出文本
- ❌ 复制 JIRA/Linear ticket 正文 —— 只引用编号
- ❌ 替用户操心"这文案该归到哪" —— 不是本工具的职责
